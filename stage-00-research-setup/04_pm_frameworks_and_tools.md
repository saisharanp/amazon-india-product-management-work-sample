# Product Management Frameworks and Tool Usage

**Project:** Amazon India user-feedback market analysis  
**Purpose:** Showcase the frameworks, methods, and product-management tools used across the product lifecycle.  
**Status:** Proposed for reviewer approval

## Portfolio narrative

This project demonstrates how a Product Manager turns unstructured customer feedback into a traceable product decision. Each framework is used for a specific decision, and each tool produces an artifact that can be reviewed by stakeholders.

The core operating model is:

**Discover → Define → Prioritize → Design → Deliver → Validate → Launch → Measure**

## Framework map by product stage

| Stage | Framework / method | How it is used | Expected artifact | Approval decision |
|---|---|---|---|---|
| Research setup | Problem framing, hypothesis tree, research canvas | Define what must be learned before collecting feedback | Research brief and hypothesis register | Approve scope and research plan |
| Discovery | Thematic analysis, affinity mapping, JTBD | Convert reviews into recurring needs, pain points, and desired outcomes | Coded feedback dataset, themes, JTBD statements | Approve evidence-backed problem area |
| Customer understanding | Personas, journey mapping, service blueprint | Show who experiences the problem and where the journey breaks | Persona and current-state journey map | Approve target segment and journey moment |
| Problem definition | 5 Whys, problem statements, opportunity solution tree | Separate symptoms from root problems and connect opportunities to outcomes | Problem statement and opportunity tree | Approve problem to solve |
| Prioritization | RICE, Value vs. Effort, confidence scoring | Rank problems using reach, impact, effort, and evidence confidence | Opportunity scoring model | Approve primary opportunity |
| Solution discovery | Design Sprint, divergent/convergent ideation, Kano | Generate multiple solutions and select an MVP direction | Concept comparison and prototype | Approve solution direction |
| Product definition | PRD, story mapping, INVEST user stories | Translate the solution into an actionable MVP scope | PRD, stories, acceptance criteria | Approve build scope |
| Delivery planning | Dual-track Agile, RACI, dependency mapping | Coordinate discovery and delivery while clarifying ownership | Release plan, RAID log, team responsibilities | Approve delivery readiness |
| Validation | Usability testing, assumption testing, experiment design | Test desirability, usability, feasibility, and viability before launch | Test plan, findings, iteration backlog | Approve changes before launch |
| Launch | Go/no-go framework, phased rollout, rollback planning | Decide whether the product is ready and control launch risk | Launch checklist and go/no-go memo | Approve launch |
| Measurement | North Star Metric, AARRR funnel, HEART, cohort analysis | Measure whether the product creates customer and business value | Metrics spec, dashboard, outcome review | Expand, iterate, pause, or retire |

## Product-management tool usage

| Tool category | Example tools | Usage in this project | Artifact / evidence |
|---|---|---|---|
| Research repository | Notion or Confluence | Store research brief, source log, assumptions, decisions, and links | Research repository and decision log |
| Feedback analysis | Excel or Google Sheets | Capture raw feedback, code themes, calculate sample frequencies, and score opportunities | CSV/XLSX datasets and scoring workbook |
| Collaboration and mapping | Miro or FigJam | Affinity mapping, journey mapping, opportunity solution tree, service blueprint | Workshop boards and exported diagrams |
| Prototyping | Figma | Create low-fidelity flows and test the approved solution concept | Prototype link and annotated screens |
| Delivery management | Jira, Linear, or Azure DevOps | Convert approved stories into epics, tasks, acceptance criteria, and release milestones | Backlog, sprint plan, release board |
| Product documentation | Confluence, Notion, or Google Docs | Maintain the PRD, decision records, launch plan, and support playbook | Versioned product documentation |
| Product analytics | Amplitude, Mixpanel, GA4, or equivalent | Define events, funnels, cohorts, retention, and experiment metrics | Tracking plan and dashboard specification |
| Customer support / feedback | Zendesk, Intercom, Freshdesk, or equivalent | Validate whether the problem appears in support contacts and measure post-launch resolution | Support theme report and issue log |
| Communication | Slack or Microsoft Teams | Share research readouts, approval requests, launch updates, and risks | Approval threads and launch communications |

## Recommended working toolchain

For a portfolio simulation, use the following lightweight stack:

1. **Google Drive or Notion:** research repository and decision log.
2. **Google Sheets or Excel:** feedback coding, sampling, scoring, and metrics model.
3. **FigJam or Miro:** journey map, affinity map, and opportunity solution tree.
4. **Figma:** prototype and usability-test flow.
5. **Jira or Linear:** MVP backlog, dependencies, and release plan.
6. **Amplitude or Mixpanel:** post-launch funnel, retention, and experiment measurement.

The tools are interchangeable. The important portfolio signal is not tool familiarity alone; it is the traceability between evidence, decision, artifact, owner, and outcome.

## Example traceability chain

| Evidence | Framework decision | Tool artifact | Product output |
|---|---|---|---|
| Repeated complaints about unclear delivery or return status | Thematic analysis + severity scoring | Feedback workbook | Ranked problem theme |
| Users describe uncertainty before purchase | JTBD + journey mapping | FigJam/Miro journey map | Trust-related problem statement |
| Several possible improvements emerge | Opportunity solution tree + RICE | Opportunity scoring workbook | Prioritized opportunity |
| One solution appears promising | Design Sprint + usability testing | Figma prototype and test report | Validated MVP direction |
| Approved solution must be built | Story mapping + INVEST | Jira/Linear backlog and PRD | Sequenced MVP release |
| Launch success must be measurable | North Star + AARRR/HEART | Analytics tracking plan | Dashboard and outcome review |

## Framework usage rules

- Use a framework only when it changes a decision or improves traceability.
- Do not score opportunities before the evidence and assumptions are visible.
- Do not treat RICE or any prioritization score as objective truth; show the inputs and confidence.
- Keep discovery artifacts separate from delivery artifacts so unresolved assumptions remain visible.
- Every approved decision should have an owner, date, rationale, and linked evidence.
- Every success metric should have an event definition, target, baseline, timeframe, and decision rule.
- Every artifact should identify whether its content is observed evidence, interpretation, assumption, or recommendation.

## Portfolio review checklist

- Can a reviewer trace the final opportunity back to actual customer evidence?
- Is the selected framework appropriate for the decision being made?
- Are prioritization scores supported by explicit assumptions?
- Do the PRD, backlog, prototype, test plan, and analytics plan describe the same MVP?
- Are approval gates visible between stages?
- Does the final outcome review compare results with the original problem and success metrics?
